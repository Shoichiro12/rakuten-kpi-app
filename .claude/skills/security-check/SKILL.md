# 週次セキュリティチェック（/security-check）

1. `date +%Y-%m-%d` で実施日を確認する
2. `security` サブエージェントに「前回チェック以降の差分を確認し、report と index を更新して」と依頼する。**差分カバレッジ節（下記）を必ず含めるよう明示的に指示すること。**
3. 返ってきた新規指摘のうち「高」があれば、その場でオーナーに報告し、対応するか判断を仰ぐ
4. 対応する場合は `developer` → `reviewer` → `qa` を通し、index の該当行を「対応済み（コミットハッシュ）」に更新する
5. 「中」「低」は未解決リストに残し、次回に持ち越す

注意: リポジトリ側 `security/index.md` とプロジェクトdocs側 `security_index.md` の二重管理問題（2026-08-24 指摘）は、どちらが正か決まるまで両方に同じ内容を書く。

## 差分カバレッジ節（必須、2026-08-31追加）

**背景**: 2026-08-31のチェック（PR #79）で「高0・中0・低0」の結論だけを見て承認しかけたところ、
オーナーの指摘で根拠不足が3件見つかった。①新設ルーターに書き込みエンドポイントが複数本あるとき、
1本だけ実測して残りは記載を紛れさせていた（例: comp-grantsの付与・解除2本のうち解除は未実測）、
②新設APIのtenancy分離に言及ゼロのまま「重点確認した」対象範囲の説明文に埋もれさせていた（一括削除
APIのtenancy）、③「本番実測は範囲外」と明記した項目を、結論サマリでは断定形で書いていた
（security-status）。**「0件」という結論は、対象範囲に含めた新規・変更コンポーネントを1つずつ
挙げて検証方法を書かない限り、根拠不足のまま通ってしまう。**

このため、報告書には結論サマリとは別に**差分カバレッジ**の節を必ず設ける。対象範囲に新設・変更
された「セキュリティ関連コンポーネント」（新規ルーター・新規テーブル・新規ガード・権限に関わる
書き込みエンドポイント）を1つずつ列挙し、それぞれ「どう確認したか」を明記する:

| コンポーネント | 検証方法 | 結果 |
|---|---|---|
| （例）`POST /api/admin/comp-grants/{id}/revoke` | 閲覧モード中POSTをローカル実測 | 403（確認済み） |
| （例）一括削除APIのtenancy | `tenancy.py::do_orm_execute`のコード追跡＋ローカル実測 | 分離を確認 |
| （例）`GET /api/security-status`の本番実測 | 本セッションからは疎通不可 | 「オーナー実測待ち」（推測で埋めない） |

守るべきこと:
- **エンドポイント単位で複数本ある新設ルーターは、1本だけ実測して他は「同じ設計だから大丈夫」と
  推測で済ませない。** 書き込み系が複数あれば全部、少なくとも各1回は実測する。
- **「範囲外」「静的レビューのみ」と書いた項目を、結論サマリでは断定形に格上げしない。** コード
  レビューでの推論と実測（ローカル/本番）は必ず書き分ける。
- 対象範囲の説明文（「〜が中心」のような1文）に、実際には検証していないコンポーネント名を
  紛れ込ませない。触れるなら検証結果とセットで書く。
