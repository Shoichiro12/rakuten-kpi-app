# 夜勤（/yakin）

これは無人・定期実行（Claude Code Routines等）から起動される想定のコマンドです。
**CLAUDE.md「🌙 夜勤の掟」を必ず先に読み、その制約に従うこと。**

夜勤は2段構成。**前段=普請**（急務を1件進める。従来からある処理）、
**後段=巡回**（発見専用。急務の有無にかかわらず毎晩実施する）。

## ⚠️ 現在のスコープ（2026-08-24導入時点）

**導入初期はコード変更禁止。調査・ドキュメント・実装計画の下書きのみ。**
バックエンド・フロントエンドのソースコード（`backend/`・`frontend/src/`等）への `Edit`/`Write` は行わないこと。
実装計画の下書き、ドキュメントの整合チェック、軽微なバグ調査、申し送り台帳・軍令帳の更新のみ許可する。
巡回（発見のみ）はこのスコープ制限とは無関係に常に実施してよい（巡回自体がコードを変更しないため）。

**この制限はオーナーが解除を台帳（CLAUDE.md「📌 申し送り」）に記録するまで有効。**
台帳に解除の記録が無い限り、何回実行されようと無期限にこのスコープを維持すること。
「もう十分実績があるはず」等の自己判断で緩めない。緩めるかどうかはPRの質を見たオーナーが決め、
決まったらオーナー自身またはオーナーの指示を受けたセッションがこの節と台帳を書き換える。

## 前段: 普請（急務対応）

1. `git status --short` と `git log --oneline -5` で現在の状態を把握する
2. CLAUDE.md冒頭の「📌 申し送り」台帳を読み、未実装・未実施の項目を確認する
3. `docs/office_map.html` の `QUESTS` 配列を読み、`stamp:"wait"`（急務）のうち先頭の1件だけを対象にする。急務が無ければ、あるいは既に評定待ちで新規に足せる情報が無ければ、この段は何もせず後段（巡回）へ進む
4. 対象の1件について、現在のスコープ（上記）でできる範囲の作業を行う
   - 「調査・ドキュメントのみ」期間中にコード修正が要る指摘だった場合は、**修正はせず** 調査結果（原因・影響範囲・修正方針の下書き）をドキュメント化するに留める
5. オーナーの判断が必要な分岐に当たったら、その時点で作業を止め、PR本文の「## 評定待ち」節に「何を」「なぜ判断が要るか」「自分の推奨案（あれば）」を列挙する

## 後段: 巡回（発見専用フェーズ）

**普請の有無にかかわらず毎晩実施する。** コード・ドキュメント・CLAUDE.md申し送り台帳を見回り、
問題を発見する。**発見しても直さない。** 修正は次の夜勤またはオーナー指示の通常セッションに回す。

1. まず `docs/gunrei_kouho.md` を読み、「候補一覧」と「却下済み」の両方を把握する
2. `docs/office_map.html` の `QUESTS`（既存の急務・後日）、`docs/gunrei_kouho.md` の候補一覧、
   CLAUDE.md申し送り台帳を見回り、コード・ドキュメントの問題点を探す
   （例: 記述と実装の食い違い、放置された古い参照、規約違反、セキュリティ上の軽微な懸念、
   ドキュメント間の矛盾など）
3. 見つけた問題を1件ずつ、次の全部と照合する。**重複するものは候補に挙げない**:
   - `docs/office_map.html` QUESTS の既存の急務・後日
   - `docs/gunrei_kouho.md` の「候補一覧」（未裁可のもの）
   - `docs/gunrei_kouho.md` の「却下済み」（一度断られたもの。**同じ指摘を形を変えて再提案しない**）
   - CLAUDE.md申し送り台帳に既に記載済みの既知事項
4. 重複を除いた新規の問題を**1晩3件まで**選ぶ。3件を超える発見があっても4件目以降は次回に回す
5. 選んだ候補それぞれについて、以下を**必ず**明記する:
   - 何が問題か
   - どこで（ファイルパスと行番号）
   - なぜ問題か
   - 放置するとどうなるか
6. `docs/office_map.html` の `QUESTS` に `stamp:"kouho"` として1行ずつ追記する（`m` は一言要約、
   詳細は `docs/gunrei_kouho.md` を見る前提でよい）
7. `docs/gunrei_kouho.md` の「候補一覧」に、5の内容を表の1行として追記する（発見日は今日の日付）
8. **候補札（`kouho`）には一切手を出さない。** 昇格（`wait`への変更）も却下（却下済みへの移動）も
   夜勤自身では行わない。それはオーナーのみが行う（CLAUDE.md「🌙 夜勤の掟」参照）

## 共通の後処理

9. 作業報告（`docs/sagyou_houkoku_yakin_YYYY-MM-DD.md`）を書く。前段（普請）で何を進め何を評定待ちに
   したか、後段（巡回）で何件の候補を見つけたかを簡潔に
10. `mainから新しいブランチを切り`、変更（普請の成果物・巡回で追記した候補、両方あればまとめて）を
    コミットする。ブランチ名は `claude/yakin-YYYY-MM-DD` 形式
11. push してPRを作成する。PR本文には「## やったこと」「## 評定待ち」「## 巡回で見つけた候補」
    「## 次にやること」の4節を必ず含める（該当が無い節は「なし」と明記する）
12. **前段・後段とも何も無かった場合**（急務なし・進展なし・巡回でも新規候補が0件）は、
    コミットもPRも作らず終了する
13. mainへのpush・マージは絶対に行わない
14. **自分で新しいスケジュールタスク・フォローアップタスクを作成しない。** PR作成後に「あとで状態を確認する」
    ための`send_later`等は仕込まず、ここで実行を完結させる。続きが必要なら11のPR本文に書いて止まる
    （CLAUDE.md「🌙 夜勤の掟」8参照）

## 触ってはいけないもの

- 本番環境変数、Stripe設定、Render/Supabase/Cloudflareのダッシュボード（アクセス権限が無い前提）
- 価格・法的文面（`billing.py`, `lp/`の価格表記等）— 触る判断自体が「評定待ち」行き
- 退会・解約・削除など破壊的操作を伴う実装
- 候補札（`kouho`）の昇格・却下（オーナーのみが行う。CLAUDE.md「🌙 夜勤の掟」参照）
