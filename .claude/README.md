# ウレシル社（Claude Code 上の仮想会社）

rakuten-kpi-app（ウレシル）の運営に必要な役割を、Claude Code のサブエージェントとスキルとして揃えたもの。
オーナー（中村祥一郎）が社長、Claude Code のメインセッションが「秘書兼PMO」、各部署はサブエージェント。

## 入れ方

このフォルダの `.claude/` を `rakuten-kpi-app` リポジトリ直下の `.claude/` にマージする（既存の `sagyou-houkoku` スキルはそのまま残す）。
`CLAUDE_md_追記.md` の内容を CLAUDE.md の冒頭「📌 申し送り」の直後に足す。
サブエージェントはセッション開始時に読み込まれるので、置いたあと一度 Claude Code を起動し直す。

## 組織図

| 部署 | エージェント名 | 主な仕事 | 権限 |
|---|---|---|---|
| 経営企画室（PMO） | `pmo` | 申し送り台帳の維持、決定事項の即時記録、未実装の棚卸し | CLAUDE.md と docs/ の編集のみ |
| 開発部・設計 | `planner` | 実装計画書（jisso_keikaku）の作成、既存実装とのマッピング | 読み取り＋docs/ 書き込み |
| 開発部・実装 | `developer` | 開発規約どおりに実装、tsc/build まで通す | フル |
| 開発部・レビュー | `reviewer` | 規約チェックリストで差分をレビュー | 読み取りのみ |
| 品質保証部 | `qa` | ローカル・本番の検証マトリクス、実測 | Bash 含む（本番は読み取り系のみ） |
| セキュリティ室 | `security` | 週次セキュリティチェック（security_index の書式） | 読み取り＋監査コマンド |
| デザイン部 | `designer` | アプリUI・LPのデザイン判断、数字と色の規則の番人 | 読み取り＋提案 |
| データ分析部 | `kpi-analyst` | KPI計算ロジック、アクション提案、アクセス軸の混在防止 | 読み取り＋提案 |
| 法務経理部 | `legal-finance` | 特商法・インボイス・価格3箇所の整合、専門家確認の要否 | 読み取りのみ |
| カスタマーサクセス部 | `customer-success` | フィードバック・解約リクエストの仕分けと返信案 | 読み取り＋下書き |
| インフラ運用部 | `infra-ops` | Render / Supabase / Cloudflare / Stripe の設定手順と月額監視 | 読み取り＋手順書 |

作業報告は既存の `sagyou-houkoku` スキルが担当（変更なし）。

## 定例業務（スキル）

| コマンド | 頻度 | 内容 |
|---|---|---|
| `/kickoff` | セッション開始時 | 申し送り台帳の未実装確認、git 状態、今日やることの確認 |
| `/jisso-keikaku` | 機能に着手する前 | planner を呼んで計画書を作り、承認を待つ |
| `/security-check` | 毎週（月曜） | security を呼んで報告書と index を更新 |
| `/release-check` | 本番デプロイ前 | reviewer → qa → 申し送り更新 → sagyou-houkoku の順で通す |
| `/price-check` | 価格・法的文面を触ったとき | legal-finance に3箇所（アプリ・LP・Stripe）の整合を確認させる |

## 流れの例

「アイテム別目標にCSV取込を付けたい」
1. `/kickoff` で状態確認
2. `/jisso-keikaku` → planner が計画書、オーナー承認
3. developer が実装、reviewer が差分レビュー
4. `/release-check` → qa 検証、pmo が台帳更新、sagyou-houkoku が報告書
5. デプロイはオーナーが実施

## 全員共通のルール

- 日本語、エムダッシュ（—）不使用、大げさな言い回しをしない
- 推測で書かない。確認した事実と未確認を分ける
- 決定事項は CLAUDE.md の申し送り台帳に「その場で」1行足す（過去に4回、決まったことが消えた）
- 法務・税務は必ず「専門家確認が必要」と明記する
- 実績・導入社数など事実でない数字は書かない（LP捏造禁止）
