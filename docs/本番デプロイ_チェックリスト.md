## 1. 法的ページのプレースホルダーを実データに置き換える

雛形には `PH` コンポーネントで**黄色ハイライトのプレースホルダー**を埋め込んである。
画面を開けば残っている箇所が一目でわかるので、全部消えるまで公開しないこと。

| 運営統括責任者 | 氏名 |

| 電話番号 | 電話番号（同上） |
| メールアドレス | 問い合わせ用メールアドレス |

> ⚠️ 返金・解約条件は**特商法表記と利用規約の2箇所**に書く。方針が決まったら両方直すこと
> （片方だけ古くなると、記載の食い違いとして一番まずい状態になる）。

> ⚠️ 文面は雛形。公開前にご自身または専門家の確認を挟むこと。

### 所在地・電話番号の掲載方針について

個人事業主の場合、「請求があったら遅滞なく開示する」体制があれば常時掲載を省略できる
場合がある（消費者庁の運用）。ただし Stripe の審査では所在地・連絡先の確認を求められる
ことがあるため、掲載する方が手続きは通りやすい傾向がある。省略する場合は、問い合わせを
受けてすぐ開示できる体制を先に整えること。

## 2. Stripe 本番（Live）設定 ※ダッシュボードでの手作業

> ⚠️ **先に新しいコードをデプロイしておくこと。** 税率(`default_tax_rates`)・
> Managed Payments の無効化・診断API は未デプロイのコードにしか入っていない。
> 古いコードのまま本番Priceに切り替えると、税額の内訳が出ないうえ
> Managed Payments に Checkout を拒否される。順番は
> **`npm run build` → コミット → push → デプロイ完了を確認 → 以下の設定**。

0. **Liveモードでも Stripe Tax（自動税計算）を無効にする**
   （設定 → 税務）。モードごとに別設定なので、テストで無効にしてもLiveには
   引き継がれない。有効のままだと手動税率と併用できず Checkout 作成が拒否される
1. モードを本番（Live）に切り替える
2. 本番用の商品・価格を新規作成
   - 金額 **¥22,000（税込）**・通貨 JPY・**継続（月次）**
   - 「価格に税金を含める」= **はい（内税）**
3. 本番用の**税率(Tax rates)**を作成し、`STRIPE_TAX_RATE_ID` に設定
   - 税率 **10%**・**「税を含む（内税）」= はい**・地域 日本
   - 請求書に「消費税 10% ¥2,000（内税）」の内訳が出る（総額は¥22,000のまま）
   - **Stripe Tax（自動税計算）は無効のままにする。** 取引ごと0.5%の手数料がかかり、
     手動税率(`default_tax_rates`)とは併用できずCheckout作成が拒否される
4. **請求書テンプレートにインボイス登録番号(T+13桁)を設定**
   （Stripeダッシュボード → 請求書のテンプレート）。適格請求書の要件
   - ⚠️ **Managed Payments は本番アカウントでも既定で有効。** コード側で
     `managed_payments={"enabled": False}` を渡して無効化しているので動作はするが、
     ダッシュボード（設定 → Managed Payments）でも無効にしておくと安全。
     Managed Payments は**日本国内取引の税務を代行しない**のに、税率指定と請求書発行を
     Stripe側が握るため、適格請求書を自分で制御できなくなる
5. 本番用 Webhook エンドポイントを設定（本番URL宛の `POST /api/stripe/webhook`）、
   本番用の署名シークレットを取得
   - 受け取るイベント: `checkout.session.completed` / `customer.subscription.created`
     / `customer.subscription.updated` / `customer.subscription.deleted`
6. 旧「コンサル付きプラン」の商品を**アーカイブ**（削除ではなく。テスト履歴を残すため）
7. Render の環境変数を本番用に更新
   - `STRIPE_SECRET_KEY` … `sk_live_...`
   - `STRIPE_PRICE_STANDARD` … 本番 Price ID
   - `STRIPE_TAX_RATE_ID` … 本番の税率 ID（**忘れると請求書に税額の内訳が出ない**）
   - `STRIPE_WEBHOOK_SECRET` … 本番用署名シークレット
   - `APP_BASE_URL` … **本番のURL**（例 `https://xxx.onrender.com`）。
     ⚠️ 未設定だと既定値 `http://localhost:5173` が使われ、**Checkout完了後に
     localhost へリダイレクトされて戻ってこられない**。既に設定済みか必ず確認する
8. 自分のカードで実際に登録 → トライアル状態を確認 → 解約、まで一通り試す
   - **14日間のトライアルがあるので、登録時点では課金されない（¥0）。**
     トライアル終了前に解約すれば料金は発生しない
9. 本番で `GET /api/billing/diagnose` を実行して全項目グリーンを確認（最速の検証）
10. 本番で `GET /api/security-status` の `unprotected` が空であることを確認

⚠️ **テストモードの Price ID / 税率 ID は本番では使えない。** Live用を別途作成する。

## 3. メール通知（コンサル問い合わせ）

Gmail のアプリパスワードを発行し（2段階認証を有効にしたうえで、Googleアカウントの
セキュリティ設定 → アプリパスワード）、Render とローカルの両方に設定する。

```
SMTP_HOST=smtp.gmail.com
SMTP_PORT=587
SMTP_USER=<Gmailアドレス>
SMTP_PASSWORD=<発行したアプリパスワード>
NOTIFY_EMAIL=<通知の宛先（SMTP_USER と同じでよい）>
```

未設定でもフォーム送信自体は成功する（通知だけスキップして警告ログを出す）設計なので、
**設定漏れに気づかないまま問い合わせを取りこぼす**のが最大のリスク。
設定後、必ず実際に送信して受信を確認すること。

## 5. 関連する実装上の約束

- **法的ページは認証ゲートの外側にルーティングしている**（`App.tsx`）。
  `/legal/*` を認証が必要な場所に移すと特商法の要件を満たさなくなるので戻さないこと。
- 価格表示は `backend/billing.py` の `PLAN_AMOUNT_LABEL`（env `PLAN_AMOUNT_LABEL`、
  既定 `¥20,000（税抜） / ¥22,000（税込）`）と、特商法ページ・利用規約 第3条の**3箇所**にある。
  値上げ・改定時は Stripe の price と合わせて全部直す。
  診断が突き合わせる `PLAN_AMOUNT_JPY`（税込・既定 22000）と
  `PLAN_AMOUNT_EXCL_TAX_JPY`（税抜・既定 20000）も同時に更新すること。
- **総額表示義務があるため、税込金額を主表記から外さない。** 税抜のみの表示にせず、
  税抜・税込を同じ視認性で並列表示する。
- **消費税は Stripe Tax を使わず、税込 ¥22,000 の固定額Priceで処理する。**
  Checkout Session に `automatic_tax` は渡さない（既定=無効）。
- ⚠️ **税抜 ¥20,000 は表示のための手計算値**（22000 ÷ 1.1）。Stripeの設定から
  自動追従しない。**消費税率が変わったら関係する全箇所を手で直す**
  （Stripeのprice / `PLAN_AMOUNT_JPY` / `PLAN_AMOUNT_EXCL_TAX_JPY` / `TAX_RATE` /
  `PLAN_AMOUNT_LABEL` / 特商法ページ / 利用規約）。
  診断が税抜表示と税込金額の割り戻し整合性を検査する。
