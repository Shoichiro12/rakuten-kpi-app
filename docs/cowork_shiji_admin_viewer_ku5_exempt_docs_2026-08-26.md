# Cowork タスク指示書: 管理者閲覧機能 区切り5（EXEMPT_TEST_EMAILS運用ドキュメント化）

対象リポジトリ: `rakuten-kpi-app`（このファイルが置かれているリポジトリそのもの）。
このファイル1本だけ読めば作業できるように、背景から書く。

## 背景

このプロダクト「ウレシル」（楽天出店者向けKPI管理SaaS）には、社内の検証・デモ用アカウントがStripeのカード登録を経ずに全機能を無料で使えるようにする仕組み `EXEMPT_TEST_EMAILS`（環境変数、カンマ区切りのメールアドレス）がある。実装は `backend/billing.py` にあり、判定は必ずJWT検証済みの認証ユーザーのメールで行う（入力値では判定しない）。

**過去にこの仕組みで実際に事故が起きている**: 2026-08-03のセキュリティ指摘を受けて既定値を `test@gmail.com` から空文字に変更するコード修正（`c4ea5b7`）が行われたが、`CLAUDE.md` の申し送り記録がその修正を3週間反映しないまま「既定値は `test@gmail.com`」という誤った記載を残し続けていた（2026-08-24に発覚・訂正済み）。**運用（誰をいつ追加・削除したか）を記録する仕組みが無いこと自体が、この種の記録漏れ・放置事故の温床になっている。** このタスクは、その運用を独立ドキュメントとして整備するもの。

このタスクは「管理者閲覧機能」という別の実装作業（`docs/jisso_keikaku_admin_viewer_2026-08-26.md` の区切り5）の一部として発注されているが、**中身はEXEMPT_TEST_EMAILSという既存の別機能の運用ドキュメント化であり、管理者閲覧機能そのものの実装・進捗とは無関係**。他の区切り（バックエンド・フロントエンド実装）を待たずに独立して進めてよい。

## やること

### 1. 新規ファイル `docs/unyou_exempt_test_emails.md` を作成する

以下の内容を含めること（見出し・表は自由に整えてよいが、内容は過不足なく含めること）:

- **概要**: `EXEMPT_TEST_EMAILS` とは何か（1〜2文。`backend/billing.py` の該当箇所を参照して正確に書くこと）
- **追加手順（オーナー作業）**:
  1. Render ダッシュボード → 対象サービス（本番: `rakuten-kpi-app-sg`、Singapore）→ Environment
  2. `EXEMPT_TEST_EMAILS` の値を編集し、既存値にカンマ区切りで追記する（例: `demo@ureshiru.com,new-test@ureshiru.com`）
  3. 保存すると自動で再デプロイされる（Renderは環境変数変更時に自動再起動する構成。手動デプロイが必要な場合は「Manual Deploy → Deploy latest commit」を使う旨も明記する）
- **削除手順**:
  1. 同じ画面から該当メールをカンマ区切りの値から削除
  2. 保存 → 自動再デプロイ
  3. **⚠️ 削除を忘れると、そのメールの受信箱を持つ人がずっと無料で全機能を使える状態が続く。** 定期的な棚卸し（例: 週次セキュリティチェック `/security-check` のタイミングで台帳と実際のRender設定を突き合わせる）を推奨する、という注意書きを入れる
- **台帳（このファイル内に表として持つ）**: 列は「追加日 / メールアドレス / 目的 / 追加した人 / 削除予定日 / 削除日」。**最初の行として、現在実際に設定されている `demo@ureshiru.com` を記録する**:

  | 追加日 | メールアドレス | 目的 | 追加した人 | 削除予定日 | 削除日 |
  |---|---|---|---|---|---|
  | 2026-07-30 | demo@ureshiru.com | トライアル運用テスト用デモアカウント | オーナー | （無期限運用のため未定） | - |

  今後 `EXEMPT_TEST_EMAILS` にメールを追加・削除するたびに、この表に行を追加・更新することをルールとして明記する。

- **既定値についての注意**: 既定値は空文字（未設定時は誰も除外されない）。過去に既定値が `test@gmail.com` だった時期があり、これが2026-08-03のセキュリティ指摘で修正されたが、記録がずれて3週間放置された事故があったことを簡潔に触れ、「台帳とRenderの実際の設定値は定期的に突き合わせること」という教訓を書く

### 2. `CLAUDE.md` の該当行に参照ポインタを1行追記する

`CLAUDE.md` の申し送り台帳（大きな表）に、行頭が「テスト・デモ用アカウントのカード登録除外」で始まる決定事項の行がある。その行の「状態」列（表の一番右のセル）は、次の文字列で終わっている:

```
...この行が3週間訂正されないままだった（詳細は下記「Coworkルーチン4週分の突き合わせ」行を参照） |
```

この末尾（閉じの ` |` の直前）に、**改行せずインラインで**（Markdownの表セルは1行でなければならないため）以下を追記する:

```
。**運用手順・追加削除の台帳は `docs/unyou_exempt_test_emails.md` を参照。**
```

つまり変更後は:

```
...この行が3週間訂正されないままだった（詳細は下記「Coworkルーチン4週分の突き合わせ」行を参照）。**運用手順・追加削除の台帳は `docs/unyou_exempt_test_emails.md` を参照。** |
```

**注意**: この行は非常に長い1行のMarkdown表セルなので、エディタの検索機能で上記の一意な文字列（`この行が3週間訂正されないままだった`）を検索して該当箇所を特定すること。行全体を書き換えるのではなく、末尾に文を追記するだけにとどめる（他の内容は一切変更しない）。

## やらないこと（スコープ外）

- `backend/billing.py` のコード変更はしない（既存の仕組みは正しく動いている。ドキュメント化のみ）
- `EXEMPT_TEST_EMAILS` の値そのもの（Renderの環境変数）を変更しない
- 管理者閲覧機能（`AdminViewSession` 等）のコードには一切触れない

## 検証

- 新規ファイルがMarkdownとして正しくレンダリングされること（表の崩れがないか目視確認）
- `CLAUDE.md` の該当行がMarkdown表として引き続き正しく機能すること（1行の中に収まっている、セル区切り `|` が壊れていないこと）
- `CLAUDE.md` の他の箇所に意図しない変更が入っていないこと（`git diff` で今回追記した1文だけが差分になっていることを確認）

## 納品方法

このリポジトリの標準運用に従い、変更はブランチを切ってコミット → プッシュ → Pull Request を作成する（mainへの直接pushはしない）。GitHub連携で push・PR作成ができない環境の場合は、`main` からの累積差分パッチ（SHA256・対象ファイル一覧つき、`git apply --check` の手順を明記）をチャット上で提示する形に切り替える。

PRの説明文には「`docs/jisso_keikaku_admin_viewer_2026-08-26.md` の区切り5に対応」と明記すること。
