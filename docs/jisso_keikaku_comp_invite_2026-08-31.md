## 1. やりたいこと（1行）

管理画面 `/admin` でメールアドレスを入れると、その相手のアカウントを作り、無償提供（comp）を
付与したうえで、招待メール（ログイン用リンク入り）をウレシルから送る。

## 2. 現状と差分

| 項目 | 現状 | 本件後 |
|---|---|---|
| comp付与 | 既存アカウントにしか付与できない（一覧から選ぶ） | メールアドレスだけで「アカウント作成＋付与＋招待」が一度に済む |
| 相手の登録手順 | 自分でサインアップ → オーナーが付与 | メールのリンクを開いてパスワードを決めるだけ |
| メール送信 | 通知（フィードバック・問い合わせ）のみ。差出人はSMTP_USERのGmail | 招待メールを追加。差出人は `info@ureshiru.com` 名義（確認事項Q1） |

## 3. 設計

### 3-1. 招待の作り方（Supabaseの標準招待メールは使わない）

Supabaseには `POST /auth/v1/invite`（Supabaseがメールを送る）があるが、文面も差出人も
Supabase側の制約を受ける。本件は「文面をこちらで作る」のが要件なので、
**`POST /auth/v1/admin/generate_link`（type=invite）でリンクだけ発行し、メールは既存の
SMTP（`backend/notifications.py`）で送る**。

- `generate_link` は対象メールのユーザーが無ければ作成し、`action_link` を返す
- 呼び出しは `routers/account.py` の `_delete_supabase_user()` と同じ方式（urllib＋service_roleキー。
  `sb_secret_` 形式のヘッダー分岐もそのまま流用）。**共通化して `supabase_admin.py` に切り出す**
- `redirect_to` は `APP_BASE_URL`（本番 `https://app.ureshiru.com`）。Supabase側の Redirect URLs に
  このURLが入っていることが前提（確認事項Q4。**2026-08-31確認済み**、§9参照）
- リンクの有効期限はSupabaseの設定（既定1時間の想定。実測して報告）。期限切れに備えて
  **「再送」ボタン**を付ける（同じ `generate_link` を再発行して再送するだけ）

### 3-2. 処理の順序（`POST /api/admin/invites`）

1. `require_admin_write`（閲覧モード中は403。compと同じ）
2. 入力チェック: `email`（形式・200文字）、`note`（必須・compと同じ運用）、`message`（任意・1000文字。メールに差し込む一言）
3. 既存アカウントの有無を Supabase Admin API で確認
   - 既にある → **409**「このメールアドレスは登録済みです。無償提供の付与は comp管理から行ってください」（確認事項Q2）
4. `generate_link(type=invite)` でユーザー作成＋リンク発行
5. 発行された `user_id` に **既存のcomp付与関数**を呼ぶ（`admin_comp.py` の付与処理を関数化して共有。
   PR #72で直した `Subscription(user_id=対象)` 明示指定の経路をそのまま通る）
6. 招待メール送信（§4の文面）
7. 監査ログに `invite_sent`（実行者・対象メール・時刻）
8. 6が失敗した場合: ユーザーとcompは作成済みのまま **502** を返し、detailに
   「アカウントと無償提供の付与は完了しています。メール送信に失敗したので再送してください」。
   一覧に「未送信」で残り、再送ボタンから送り直せる（作り直しはしない）

`POST /api/admin/invites/{user_id}/resend`: 同じ手順の4と6だけ。監査ログは `invite_resent`。

⚠️ **手順4（`generate_link`）が成功したあと、手順5（comp付与）や手順6（メール送信）で
失敗した場合、Supabase側のユーザーは作成済みのまま残る**（手順8の「作り直さない」設計は
手順6の失敗を再送ボタンで回収する前提で、手順5より前の失敗を想定していない）。この状態で
同じメールに `POST /invites` を再実行すると、手順3の存在確認に引っかかって **409**
になる（招待ではなく「既存アカウントへの付与」を促す文言が返る）。**再実行したい場合は、
先にSupabaseダッシュボード（Authentication → Users）で該当ユーザーを手動削除してから
改めて招待すること。** comp管理（既存アカウント向け付与）から手動で付与を完了させる方法もある。

### 3-3. データ

新テーブルは作らない。`comp_grants` に列を2つ足す:

| 列 | 型 | 用途 |
|---|---|---|
| `invited_at` | datetime NULL | 招待メールの最終送信日時（NULL＝招待経由でない通常のcomp付与） |
| `invite_status` | text NULL | `sent` / `failed`。一覧の表示用 |

「初回ログイン済みか」は Supabase の `last_sign_in_at` を一覧取得時に引く（DBに持たない）。

### 3-4. フロント（`/admin` のcomp管理セクション）

- 「メールで招待」ブロックを追加: メール・理由（必須）・メッセージ（任意）・**送信前プレビュー**
  （実際に送る本文をそのまま表示）・「招待メールを送る」ボタン。確認ダイアログは既存 `ConfirmDeleteModal` を流用
- comp一覧に「招待」列: 送信日時 / 未送信 / ログイン済み（`last_sign_in_at` あり）と「再送」ボタン
- 既存のcomp付与フォーム（既存アカウント向け）はそのまま残す。**入口を2つにするだけで、付与のロジックは1つ**

### 3-5. 招待された側の画面

リンクを開くと Supabase 経由で `APP_BASE_URL/#...&type=invite` に戻ってくる。
既存の `ResetPassword.tsx` は `PASSWORD_RECOVERY` イベントで出しているので、
**URLハッシュの `type=invite` でも同じ画面を出す**（見出しだけ「パスワードを設定してください」に切替）。
設定後はそのままダッシュボードへ。compが付いているので課金導線は出ない（comp区切り2で実装済みの分岐）。

補足: Googleログインは本番で無効（`VITE_ENABLE_GOOGLE_LOGIN` 未設定＝ボタン非表示）のため、
招待された人の入口はメール＋パスワードだけ。メール本文でもGoogleログインには触れない。
将来Googleログインを有効化したときは、同じメールなら Supabase が同一アカウントに自動リンクするので
本件の作りは変えなくてよい（文面に一段落足すだけ）。

## 6. 検証

区切り2（ローカル・実測）:
- 閲覧モード中の招待・再送が403
- note空が400（compと同じ方式）、email形式不正が400、既存アカウントが409
- 招待成功で: Supabaseにユーザーが出来る / `comp_grants` に対象user_idで行が出来る /
  `Subscription` が対象user_idに作られ管理者自身の行は変わらない（PR #72の恒久項目）/ 監査ログ1件
- SMTP未設定・送信失敗時: ユーザーとcompは残り、502、`invite_status=failed`、再送で `sent` に変わる
- 再送でユーザーもcompも増えない（冪等）
- `{message}` 空のときに空行が残らない

区切り4（本番・オーナー）:
- 自分の別アドレス宛に招待 → メールが `info@ureshiru.com` 名義で届く（迷惑メール判定もここで見る）
- リンクを開いてパスワード設定 → ダッシュボードが開き、`/billing` に課金導線が出ない
- 期限切れリンクを踏んだときの表示が「再送を依頼してください」相当になっている
- 一覧に「ログイン済み」が出る
- `/api/security-status` が `ok: true` のまま（列追加のみだが念のため）
- 終わったらテスト用の招待はcomp解除＋Supabaseからユーザー削除

**結果（2026-09-01、オーナー実施）: 全項目PASS。** 差出人「ウレシル `<info@ureshiru.com>`」名義で
受信トレイに着信（迷惑メール扱いなし）／リンクからパスワード設定→ログイン→無償提供中の表示・
課金導線なしを確認／`/admin`の招待列に送信日時が表示されることを確認。**これで区切り4も完了**。

## 8. 注意

1. **service_roleキーはバックエンドのみ**。`supabase_admin.py` をフロントから参照できる場所に置かない
2. `generate_link` の `action_link` はログに出さない（開けばログインできるリンクなので）。ログは対象メールと結果だけ
3. Gmail SMTPで `From: info@ureshiru.com` を出すには、Gmail側の「名前を指定して送信」に登録済みであることが条件
   （2026-07-30に3アドレス登録済み。記録はClaudeプロジェクト内の資料〈リポジトリ外〉）。
   未登録アドレスを From にするとGmailが SMTP_USER に書き換えるので、区切り4で差出人表示を必ず目視
4. 招待は1件ずつ手動で送る前提。連打防止として同一メールへの再送は前回から60秒空ける（それ以上の制限は入れない）
5. `_send` に from/to を足すとき、既存の通知メール（NOTIFY_EMAIL宛）の挙動を変えないこと
