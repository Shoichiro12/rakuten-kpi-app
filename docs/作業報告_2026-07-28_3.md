## 3. 見つけて直したバグ・設定ミス 7件

### ① Managed Payments が既定で有効で、税率の指定を拒否していた（影響: 大）

Checkout作成が `Unsupported parameter: subscription_data.default_tax_rates.
Managed Payments, which is enabled by default on your account, handles taxes for you.` で失敗した。

Managed Payments は Stripe が merchant of record になる仕組みで、**Stripeアカウントで既定で有効**。
調べた結果、**日本国内取引の税務は代行しない**ことがドキュメントに明記されていた
（間接税を扱うのはシンガポールB2B国内と日本の全国内取引を「除く」国）。
つまり国内向けの当サービスでは消費税の責任は自分に残る一方、税率指定と請求書発行だけ
Stripeに握られ、適格請求書を自分で制御できなくなる。得るものが無いので
`managed_payments={"enabled": False}` を明示的に渡して無効化した。
アカウント設定でも切れるが、既定が有効なのでコード側で明示している。

### ② 消費税が加算されず税抜額しか請求されない状態だった（影響: 大）

**原因は私の思い込み。** Stripeのpriceは税込で登録するものと決めつけ、
外税(`tax_behavior=exclusive`)＋ Stripe Tax の構成を想定していなかった。
Checkout に `automatic_tax` を渡していなかったため、税が加算されず¥20,000しか
請求されない状態だった（表示は税込¥22,000）。

気づきにくかった理由: **Stripeダッシュボードの価格プレビューは税計算込みの見積り**を出す。
「小計¥20,000 / 消費税¥2,000 / 合計¥22,000」と表示されるので、実際のセッションで
税が加算されるかとは別の話だと分かりにくい。

さらに私は途中で**誤った指示**（「Priceを¥22,000で作り直してください」）を出した。
ユーザーから外税設定である旨の指摘を受けて構成を正しく理解した。
最終的には方針変更（下記④）でこの構成自体を採用しなかった。

### ③ `current_period_end` が常にNULLだった（影響: 中）

stripe-python 15.3.1 はAPIバージョン `2026-06-24.dahlia` を送る。このバージョンで
`current_period_end` は **Subscriptionオブジェクトから削除され、Subscription Item側へ移動**している。実測:

```
stripe.Subscription     のソース内 current_period_end: 0箇所
stripe.SubscriptionItem のソース内 current_period_end: 1箇所（int）
```

DBの値が常にNULLで、契約中の画面に「次回更新: —」と出ていた。
item → サブスク直下の順で読む `_current_period_end()` を追加し、新旧どちらの
APIバージョン形式でも値が入ることを両方テストで確認した。

### ④ Checkout完了後の同期エラーが無言だった（影響: 大）

`api.billing.confirm(sid).catch(() => {})` でエラーを捨てていた。Stripe側は登録できて
いるのに同期に失敗すると**何も表示されずプラン選択画面に戻る**ため、
「登録したのにサブスクになっていない」という当初の報告そのものの見え方になっていた。

### ⑤ Checkout失敗メッセージが原因を隠して誤誘導していた（影響: 中）

失敗時の文言が「Stripeキーの設定を確認してください」に固定され、Stripeが返す実際の理由
（Priceがアーカイブ済み、Managed Paymentsの拒否など）が捨てられていた。キーは正常だったので
誤誘導になる。①の原因特定が可能になったのはこの修正のおかげ。

### ⑥ 診断の金額チェックが円で誤検知した（影響: 小・自分のバグ）

円はStripeの zero-decimal currency で `unit_amount` が円そのまま（¥22,000 → 22000）。
ドル等のセント単位と混同して100倍で比較していた。定数と比較する形に修正。

### ⑦ 解約済み契約に対して無意味なエラーを出していた（影響: 小・自分のバグ）

診断が、解約済みの契約に対して「税率が付いていないので作り直してください」と
error を出していた。再登録前は必ず出るノイズなので、`canceled` / `incomplete_expired` の
ときは契約単位のチェックを省略して案内文だけ出すようにした。

## 4. 調査の結論: 「トライアルが効いていない」

**コード側・Stripe設定側ともに問題なし。** 原因は次のとおり。

- 通常プラン: 07/24登録 → トライアル終了08/07（ちょうど14日）で**正常だった**
- コンサル付きプラン: 支払いの説明が `Subscription update` で、カスタマーポータルからの
  プラン変更で作られたサブスクだった。**Stripeはプラン変更時に `trial_period_days` を
  再適用しない**ため `trialing` を飛ばして `active` になり即課金された。仕様どおりの挙動

なお顧客が2つに分かれていた点を当初「不具合の可能性」と指摘したが、2プランをそれぞれ
検証した経緯からすれば自然な状態で、私の指摘が的を外していた。

## 7. 申し送り3件への結論

### ① コンサル問い合わせ記録を退会時に消すか → **消さない（現状維持）**

`DELETE /api/account` の削除対象 `_ALL_MODELS` に `ConsultingInquiry` を入れない。
**プライバシーポリシー第5条で既に「コンサルティングサービスへのお問い合わせ記録（営業記録として）」
は退会後も保持する場合があると明記しており、実装と表記が一致している。**
`Subscription`（会計・税務記録）を残しているのと同じ扱い。

コード変更なし。ただし本人から削除依頼が来た場合に備え、DBを直接消せる運用にしておく
（管理画面は作っていないので手作業になる）。

### ② Stripe顧客の重複防止 → **入れることを推奨。ただし本番公開のブロッカーではない**

現状は、Checkout完了後の同期（Webhook or `/confirm`）が両方失敗すると DB に
`stripe_customer_id` が残らず、次回の登録で**新しいStripe顧客が作られる**。
本番はWebhookが動くので発生確率は低いが、起きると同一利用者の請求履歴が
2つの顧客に分かれて調査が面倒になる。

実装方針: Checkout作成前に、DBに顧客IDが無ければ `AuthUser.email`（JWTに入っている）で
Stripeの顧客を検索し、あれば再利用・無ければ作成して、そのIDを常に渡す。15行程度。
副作用として、Checkout未完了でも顧客が先に作られる（空の顧客が残る）点は許容範囲。

優先度: 中。公開後でも入れられる。

### ③ 支払い失敗（`invoice.payment_failed`）の扱い → **UIの穴を先に塞ぐべき。Webhook追加は後でよい**

※ これは私が明示的に申し送りに挙げていなかった項目だが、確認したところ実際にギャップがある。

- **状態同期は足りている。** 支払いが失敗すると Stripe がサブスクの status を `past_due` に
  変え、それが `customer.subscription.updated` として飛ぶ。このイベントは既に
  `_HANDLED_EVENTS` に入っているので、DBの status は `past_due` に更新される。
  つまり `invoice.payment_failed` を追加しなくても状態は追随する。
- **UIに穴がある。** `_ACTIVE_STATUSES = ("trialing", "active")` なので `past_due` は
  `is_active=false` になり、`Billing.tsx` は「現在のご契約」ブロックを出さずに
  **プラン選択カードを表示する**。支払いに失敗した利用者に「未契約です」と見える状態で、
  何が起きたか分からず問い合わせになる。`STATUS_LABEL` に `past_due: '支払い遅延'` は
  定義済みだが、契約中ブロック内でしか使われていないため表示されない。

推奨対応（公開前）: `past_due` / `unpaid` のときは専用のメッセージを出す。
「お支払いの確認が取れていません。カード情報をご確認ください」＋カスタマーポータルへの
ボタン。Stripeのスマートリトライが自動で再試行するので、こちらから能動的にやることは
ポータルへの導線を出すことだけ。10行程度。

`invoice.payment_failed` の Webhook 追加は、**支払い失敗時に自分へ通知メールを送りたい**
場合にのみ必要。今は不要と判断。

## 9. 注意点・申し送り

### Stripeまわり（今回ハマった順）

- **Managed Payments は既定で有効。** `managed_payments={"enabled": False}` を消すと
  `default_tax_rates` が拒否されてCheckoutが失敗する。日本国内取引の税務は代行してくれない
- **Stripe Tax（自動税計算）は使わない。** 手動税率と併用できず、取引ごと0.5%かかる
- **税率は既存契約に遡らない。** 税率を追加・変更したら契約を作り直す必要がある
- **ダッシュボードの価格プレビューは税計算込みの見積り。** それだけ見て判断しない
- **`.env` を書き換えたらバックエンドを完全再起動する。** `uvicorn --reload` は `.py` の
  変更しか監視しない（今回2回これで混乱した）
- **モードごとに別設定**: Price / 税率 / 登録番号 / Webhook / Stripe Tax / Managed Payments
- 価格まわりを触ったら `GET /api/billing/diagnose` を必ず実行する

### 価格の記載箇所（改定時は全部直す）

| 場所 | 値 |
|---|---|
| `backend/billing.py` `PLAN_AMOUNT_LABEL` | 表示文字列 |
| `backend/billing.py` `PLAN_AMOUNT_JPY` / `PLAN_AMOUNT_EXCL_TAX_JPY` / `TAX_RATE` | 診断の期待値 |
| `frontend/src/pages/legal/Tokushoho.tsx` | 販売価格 |
| `frontend/src/pages/legal/Terms.tsx` 第3条 | 利用料金 |
| Stripeのprice / 税率 | 実際の請求額 |

**税抜¥20,000は手計算値**（22,000÷1.1）でStripeから自動追従しない。
総額表示義務があるので税込金額を主表記から外さない。診断が割り戻しの整合性を検査する。

### その他

- **`/legal/*` を認証必須の場所に移さないこと。** 特商法は購入前の表示を求めており、
  Stripeの審査でも購入手続き前に到達できるURLかが確認される
- **法的ページの文面は雛形。** 私は弁護士でも税理士でもないので、公開前にご自身または
  専門家の確認を挟むこと。特に**インボイス（適格請求書）の様式・登録番号の記載方法**は、
  Stripeが発行する請求書をそのまま顧客に渡す形になるため、税理士にプレビューを
  見てもらう価値がある
- `consulting_inquiries` のRLSは起動時の `_enforce_rls_pg()` が自動適用する。
  デプロイ後に `GET /api/security-status` で `unprotected: []` を確認すること
- **SMTP未設定でも問い合わせ送信は成功する設計**なので、設定漏れに気づかないまま
  問い合わせを取りこぼすのが最大のリスク
