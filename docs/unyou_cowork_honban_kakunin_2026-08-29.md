# 運用手順: 本番デプロイ確認のCowork/Chrome委任

**位置づけ**: Claude Codeセッションから本番URL（`https://app.ureshiru.com`）へ疎通できないとき
（`docs/gunrei_kouho.md`「デプロイ後定型確認のCowork委任化」候補・2026-08-29に手順化してクローズ）、
デプロイ完了確認と簡易回帰をCowork（Chrome拡張でブラウザ操作ができるセッション）へ委任する手順。
2026-08-29、[PR #75](https://github.com/Shoichiro12/rakuten-kpi-app/pull/75)（マスタ削除区切り1）の
本番確認で初めて実施し、機能することを確認した。

## いつ使うか

Claude Codeセッション側で `curl` 等が本番URLへ疎通しない（プロキシの `403 gateway policy denial` 等）と
判明したとき。疎通できるセッションでは従来どおり `curl` での確認を優先する（Cowork委任は疎通不可の
ときの代替手段であり、既定の手順ではない）。

## 許可する操作範囲（必ず守ること）

**読み取り専用 + 管理者閲覧モードの開始/終了ボタンのみ。それ以外のボタン操作・入力・削除・保存は
一切行わない。**

- 許可: ページの表示確認、スクロール、コンソールログの確認、管理者閲覧モードの「閲覧を開始」
  「閲覧を終了」ボタンのクリック（対象アカウントの画面を読み取り専用で見るために必要）
- 禁止: フォーム送信、削除ボタン、保存ボタン、CSVインポート、契約状態を変える操作（comp付与・解除等）、
  設定変更全般。管理者閲覧モードは「読み取り専用」を技術的に強制する仕組み（`backend/auth.py` の
  `UserContextMiddleware`。GET/HEAD/OPTIONS以外は403）だが、**管理者アカウント自身の操作
  （`/api/admin/*`）はこの強制の対象外**（閲覧セッション管理そのものがデッドロックしないための
  意図的な除外。詳細はCLAUDE.md「管理者閲覧モード」節参照）なので、`/admin`画面上の削除・付与系
  ボタンは技術的にブロックされない。**したがって許可範囲はコード側の強制ではなく、委任時の指示で
  明示的に絞ること。**

## 確認する項目（デプロイ後の簡易回帰）

1. `https://app.ureshiru.com/api/health` が200を返すこと（デプロイ後のプロセスが生きていることの確認）
2. 変更が関係する画面を開き、表示が壊れていないこと（レイアウト崩れ・エラーバナー等が無いこと）
3. ブラウザのDevToolsコンソールにエラーが出ていないこと（0件）
4. **既存のUI要素が従来どおりであること**（例: 単体削除ボタンの位置・文言が変わっていない）
5. **今回のPRのスコープに含まれないUIが増えていないこと**（例: バックエンドAPIだけを実装した区切りでは、
   対応するフロントUI＝チェックボックスや一括削除ボタンがまだ画面に出ていないのが正しい。フロント未実装の
   区切りで新しいボタンが見えてしまったら、想定と違うコードがデプロイされている可能性があるため要調査）

## 記録の残し方

確認結果は該当PRの申し送り台帳の行（CLAUDE.md）・`docs/office_map.html`のQUESTSに、確認した項目と
結果を簡潔に追記する。「本番確認完了」とだけ書かず、**どの委任先で・どの範囲の操作許可で・何を確認したか**
まで書く（今回のように後から「Cowork初回委任だった」という文脈が失われないようにするため）。

## 実績（2026-08-29、初回実施）

PR #75（マスタ削除一括化 区切り1・バックエンドAPIのみ）の本番デプロイ確認をCowork/Chrome拡張へ委任し、
以下を確認した:

- `https://app.ureshiru.com/api/health` 200
- カテゴリマスタ・商品マスタなど関連4画面の表示が正常
- ブラウザコンソールエラー0件
- 既存の単体削除ボタンは従来どおり
- 一括削除UI（チェックボックス・一括削除ボタン）は画面に出ていない（**区切り1はバックエンドのみで
  正しい。区切り2/3で実装予定**）

許可した操作は読み取り専用の閲覧＋管理者閲覧モードの開始/終了ボタンのみ（本ドキュメントの範囲どおり）。
詳細はCLAUDE.md申し送り台帳「マスタ削除の一括化と未分類フロー」行を参照。
