## 1. いちばん重要な制約: 書けないものがある

Hallmark は「実在しない数値・証言・ロゴを書くこと」を禁止している（gate 46）。現状のウレシルには次が**存在しない**。

- 顧客の声・導入事例（VISION.md のKPIは「成功事例5社」＝これから作る段階）
- 導入社数・改善率などの実績数値
- 掲載可能な導入企業ロゴ（アイズ社は2026-08-07時点でトライアル運用テストの段階。出すなら**先方の許諾が要る**）

**この制約が構成を決める。** 借り物の信頼（お客様の声・ロゴウォール・「売上◯%改善」）が使えない以上、信頼は**製品が実際に仕事をしている様子**でしか作れない。よって:

- 却下: Stat-Led（巨大な数字がヒーロー）、Quote-Led（証言がヒーロー）→ どちらも数値・証言の捏造なしには成立しない
- 標準SaaS構成から**ロゴウォールと顧客の声の2セクションを外す**
- 代わりに**製品の実画面と、それが出す判断そのもの**を前面に置く

## 2. 骨格の決定（Hallmark critical 3件への回答）

### マクロ構造: **14 · Narrative Workflow**（工程の物語）

段階（1.0 → 2.0 → …）が縦に連なる構造。各段階に見出し・短い説明・実画面が付く。

なぜこれか:

1. **VISION.md の中身そのものだから。** ウレシルは「ダッシュボードを見せる製品」ではなく「取り込む→わかる→決める→動く→効く」を毎週回す製品。工程構造はその主張と一致する。機能を3つ並べる現構成は、この主張を伝えられない。
2. **3カラムグリッドが構造的に消える。** 段階は順序を持つので縦に連なる。「グリッドを使わない」と決めるのではなく、**使う理由がなくなる**。
3. **現状のテンプレ骨格と categorically に違う。** 現構成（hero → 課題3枚 → 機能3つ交互 → 3ステップ → 料金 → FAQ → CTA）は定型そのもの。

代替案として **05 · Workbench**（実画面が主役の操作ツアー）も適合する。Workbench のほうが製品の具体性は強く出るが、「毎週回るループ」という主張は弱くなる。**推奨は Narrative Workflow。**

### ナビ: **N9 · Edge-aligned minimal**（ロゴ左・CTA右・間は空白）

- 現状の「ロゴ＋機能/料金/FAQ/使い方＋CTAボタン」は Hallmark が**最も典型的なAIの指紋**として名指ししている形（N1a）。critical「AIナビ」はこれを指していたとみて間違いない。
- N9 はリンク行を持たないので、**640px以下でナビ項目が全部消える現在のバグ（`lp/index.html:193`）が構造的に起きない**。
- 面内の位置把握は工程番号（1.0〜5.0）が担う。料金・FAQへの導線はフッターと、ヒーロー直下の小さな目次で確保する。

代替: **N6 · Newspaper masthead**（大きな中央ロゴ＋細い日付行＋罫）。日本語エディトリアルの雰囲気は強まるが、B2Bツールとしては装飾的に振れる。

### フッター: **Ft1 · Mast-headed**

- ロゴ＋一行のタグラインが帯を締め、その下に法的リンクを並べる。
- **法的リンク5本（ヘルプ・特商法・プライバシー・利用規約・お問い合わせ）は必ず全部残す。** Stripe審査が見るのはLP側で、購入導線から法的文書へ到達できることが要件（`lp/README.md`）。
- 現状の「リンク行＋ブランド」も悪くはないが、Hallmark が忌避する4カラム索引フッター（Ft3）に近づけないこと。

## 4. オーナーに決めてほしいこと

実装（ステップ3）に入る前に要る判断。**1〜3は構成そのものが変わるので、着手前に必要。**

1. **家具特化を打ち出すか。** VISION.md は「楽天市場 × 家具業界」から入ると明記しているが、現LPは楽天全般向けの汎用文言。家具に寄せるとアイズ社・LOWYA等への刺さりは上がるが、他カテゴリからの自然流入は落ちる。**現状は汎用のまま維持を推奨**（self-serveの登録導線が既にあるため）。
2. **アイズ社のトライアルを実績として出すか。** 出すなら先方の許諾が要る。許諾が取れれば「顧客の声」セクションが復活し、構成の説得力が大きく変わる。**取れないうちは書かない**（捏造になる）。
3. **スクリーンショットを誰がいつ撮るか。** 全撮り直しが必要。デモアカウント（`demo@ureshiru.com`）のサンプルデータで撮るのが安全（実店舗データは出せない）。**これが揃わないと工程スパインは絵にならない**ので、実装のクリティカルパス。
4. ナビは N9（推奨）か N6 か。
5. C案トーン維持でよいか（推奨: 維持）。

## 8. 受領実績（2026-08-07・オーナーがブラウザから撮影）

Cowork ではなくオーナーが自分のブラウザから撮影して受領。`lp/` に配置済み（SHA256一致を確認）。**仕様と3点違うので、仕様側を現物に合わせて改訂した。**

### 改訂1: 形式は JPEG のまま（PNG変換しない）

| | |
|---|---|
| 受領 | JPEG 6枚・合計 446 KB |
| 判断 | **JPEGのまま採用。変換しない** |

**理由: JPEG→PNG変換は無意味だから。** JPEG圧縮で失われた情報は変換で戻らず、「同じ劣化＋ファイルサイズ増」になるだけ。選択肢は「JPEGのまま」か「PNGで撮り直す」の二択で、後述の表示幅制約を守れば JPEG で実用上の劣化は出ない。LPの表示速度の点でもJPEGが有利。

**拡張子は `.jpg` にした**（`shot-hero.png` ではなく `shot-hero.jpg`）。中身がJPEGのファイルに `.png` を付けると、拡張子を信頼するツールで事故る。

### 改訂2: 実寸 1568 × 706（DPR1）→ **LP上の表示幅を 780px 以下に制限する**

仕様は 1440×900 @DPR2（実効 2880×1800）だったが、実物は **1568×706 の等倍**。

**これは実装側の制約に翻訳できる。** 網膜ディスプレイ（DPR2）で滲まずに出せるCSS表示幅は `1568 ÷ 2 = 784px`。よって:

> **工程スパインの実画面は `max-width: 780px` で配置する。ヒーローの主役カットも同じ上限。**

Narrative Workflow は元々「各段階に小さめの実画面」を置く構造なので、この制約は設計と矛盾しない。むしろ 1120px の `.wrap` に対して約70%になり、収まりが良い。**780pxを超えて引き伸ばさないこと**（超えた瞬間に滲む）。

高さ706pxが短い点は、工程スパインでは**むしろ好都合**（各段階の要点だけに焦点が絞れる）。フルページスクショは不要。

### 改訂3: `shot-5-learn.jpg` は**このままでは使えない**

「実施した施策のその後」の4件が**全部「2026-09 の実績待ち」**で、効果検証の数値が1つも入っていない。

**原因はサンプルデータではなく日付。** この機能は「実施した月と翌月の実績を比較」する仕様。撮影日が 2026-08-07 で、施策の実施月が 2026-08 なので、比較対象の 2026-09 はまだ存在しない。**当月に実施した施策は構造上かならず「実績待ち」になる。**

**このまま載せると逆効果。** 「施策のその後」が全件「待ち」の画像は、機能が動いていない証拠に見える。5.0「効く」の段階は学習ループ（VISION Phase 2）の唯一の証拠なので、ここが空だと工程スパインの主張が成立しない。

| B | 5.0 は画像なしで公開し、Aが済んだ段階で差し替える | 小 |
