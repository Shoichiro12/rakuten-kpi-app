# 実装計画: アイテム別目標の一括入力UI（2026-08-03）

対象: `item_targets`（アイテム別目標売上）の入力を、現状の「1件ずつ」から複数まとめて入力・保存できる形にする。
本ドキュメントは指示書「目標設定の一括入力UI 指示書（2026-08-03）」への調査結果・方式比較・確認事項回答案・実装計画。**レビュー後に実装へ進む前提**（まだコードは触っていない）。

---

## 1. 調査結果（現状）

### 1-1. 現状の入力画面

該当は `frontend/src/pages/TargetSetting.tsx` の「アイテム別目標」セクション（550行目〜）。
**現状すでにテーブル形式**で、対象月の商品を1行ずつ並べている。

- 行の母集団: `GET /api/item-targets?year_month=YYYY-MM` が返す「商品マスタの稼働中商品 ＋ 実績データにある商品 ＋ 目標設定済み商品」の和集合（廃盤除外・管理番号順）。目標未設定の商品も `target=null` で行に出る。
- 各行の「目標売上（入力）」は uncontrolled な number input（`defaultValue` ＋ `onBlur`）。
- 目標CVR・客単価・必要アクセス・根拠は表示専用（自動算出結果）。承認/再計算ボタンは推定値の行だけに出る。

### 1-2. 現状の保存フローとボトルネック

1つのセルを編集して離れる（onBlur）たびに:

1. `saveItemTarget(mno, value)` が `POST /api/item-targets`（**1件だけ**）を呼ぶ
2. 成功後に `loadItemTargets(yearMonth)` で**一覧を丸ごと再取得**して再描画

つまり **N件入力すると「N回のPOST＋N回の全件リロード」** になる。これが「1件ずつしか入力できない」＝手間が大きい、の実体。アイテム数が多い店舗ほど、タブ移動のたびに通信と全再描画が挟まって重い。

さらに、絞り込み手段が無く**常に全商品を一覧表示**するため、アイテム数が多いと目的の商品を探すのも大変。

### 1-3. バックエンドAPI現状（`backend/routers/item_targets.py`）

| エンドポイント | 役割 |
|---|---|
| `GET /api/item-targets?year_month=` | 対象月の一覧（未設定含む） |
| `POST /api/item-targets` | **1件**のupsert。保存時に `calc_item_target` で目標CVR・客単価・必要アクセスを自動算出して保存 |
| `POST /api/item-targets/approve` | 推定値（参考値）の承認 |
| `POST /api/item-targets/recalc` | 1件の明示再計算 |
| `DELETE /api/item-targets/{mno}` | 1件削除 |

- 自動算出は `target_calc.py` の確定公式 MIN(現状値, 前年値)。`calc_item_target` は1件あたり概ね3〜5クエリ（直近実績・前年同月、実績ゼロ時のみ同ジャンル推定で数クエリ追加）。
- 保存する手入力値は `target_sales` のみ。他は導出値。
- ソースコメントにも「一括入力は別チケット」と明記されている（＝今回のチケット）。

### 1-4. 既存の一括入出力資産（`backend/routers/masters.py`）

商品マスタに **CSV export/import が既にある**（`export_master_products` / `import_master_products`）。今回そのまま流用できる作法が揃っている:

- 出力: BOM付きUTF-8、`csv.writer`、`Content-Disposition` に日本語ファイル名（`filename*=UTF-8''...`）。
- 入力: `utf-8-sig / utf-8 / cp932 / shift_jis` の順でデコード試行 → `pandas.read_csv(dtype=str).fillna("")` → 管理番号キーで upsert → 最後にまとめて再計算 → 件数を返す。

**結論: CSV方式を採るなら、この作法（エンコード判別・BOM・pandas・管理番号upsert・件数レポート）はほぼコピーで再利用できる。** ただし item_targets は「対象月」という次元が増えるので、CSVに `対象月` 列を持たせるか、月ごとに1ファイルにするかの設計が要る（後述）。

## 2. 方式比較: テーブル一括編集 vs CSV入出力

| 観点 | テーブル一括編集（複数行を編集→1回で一括保存） | CSV入出力（エクスポート→Excel編集→インポート） |
|---|---|---|
| 実装コスト | 中（フロントに編集状態の保持＋一括保存ボタン、バックエンドに一括保存API1本） | 中〜低（masters.pyの作法を流用。ただし対象月次元の設計と、往復用のエクスポートが要る） |
| 使い勝手（少数の微修正） | ◎ 画面上で即編集・即反映。ファイル往復なし | △ ダウンロード→Excel→アップロードの往復が毎回必要 |
| 使い勝手（大量アイテムの一括入力） | ○ 絞り込みと併用すれば実用的。ただし数百件を画面で打つのは限界あり | ◎ Excelで一気に埋められる。コピー＆フィルも効く |
| 大量アイテム対応 | 絞り込み前提でカバー | ◎ 件数に強い |
| オフライン編集 | ✕ | ◎ Excelで可能 |
| 即時フィードバック（算出結果） | ◎ 保存直後に必要アクセス等が返る | △ 取込後に一覧で確認 |
| 学習コスト | 低（今の画面の延長） | 中（列仕様・往復手順の理解） |

### 推奨

**まず「テーブル一括編集」を本命として実装し、CSVは任意の第2段階とする。**

理由:
- 今回の痛点は「1件ずつのPOST＋毎回全件リロード」という**保存フローの非効率**であって、これはテーブル一括保存で直接解消できる。今の画面の延長で学習コストも低い。
- 大量アイテムは「絞り込み（後述Q2）」との併用でカバーできる。
- CSVは実装資産があるので後付けが安い。数百SKU級の店舗から「Excelで一気に入れたい」要望が実際に出た段階で第2段階として足すのが、コスト対効果のバランスが良い。両方を最初から作り込むと、対象月次元のCSV設計まで抱えて初回スコープが膨らむ。

## 3. 確認事項への回答案（要レビュー）

### Q1. 保存方式: 個別API vs 一括1リクエスト

**回答案: 一括1リクエストにする。新規 `POST /api/item-targets/bulk` を追加する。**

- リクエスト: `{ year_month: "YYYY-MM", items: [{ management_no, target_sales }, ...] }`
- 挙動: 各 item を既存 upsert と同じロジック（`calc_item_target` で自動算出）で処理し、**1トランザクションでまとめて commit**。レスポンスで保存後の各行（`_to_dict` 相当）と件数を返す。フロントは**保存後に1回だけ**一覧をリロード。
- 既存の `POST /api/item-targets`（1件）は残す（onBlur即時保存を使いたい場面や後方互換のため）。bulk は既存 upsert のロジックを共通関数に切り出して再利用し、**算出式が二重実装で食い違わないようにする**。
- 補足（性能）: `calc_item_target` は1件あたり数クエリなので、bulk で N件回すと N×数クエリになる（`CLAUDE.md` の revenue_plan プリフェッチ規約と同じ論点）。ただし本APIは利用者が明示的に押す低頻度操作で、かつ**確定公式のコードパスを1件保存と完全共有できる正確性メリットが大きい**ため、**初版は素直なループで実装**することを提案。数百SKU級で体感遅延が出たら、そのときプリフェッチ最適化を別途行う（初版ではやらない）。この判断でよいか要確認。

### Q2. 一括入力の対象: 全件常時表示 vs 絞り込み前提

**回答案: 絞り込み前提にする。** アイテム数が多い店舗を想定すると全件常時表示は扱いづらい。

- 絞り込み軸（案）:
  1. **キーワード検索**（商品名・管理番号の部分一致。フロント側で実施）
  2. **未設定のみ表示**（`target == null` の商品だけ。埋め漏れを潰す用途。フロント側で実施）
  3. **ジャンル絞り込み**（大/中分類。※現状の一覧APIはジャンルを返していないので、レスポンスに `genre_u1/u2/u3` を追加する小改修が要る。値は直近実績（MonthlyItemSales）優先、無ければ商品マスタのカテゴリから解決）
- 「一括保存」は**現在の絞り込み結果のうち編集した行だけ**を送る（画面に出ていない行は触らない）。これにより「絞り込んで一括編集→一括保存」が自然に成立する。
- 検索・未設定フィルタはフロント完結で足せる。ジャンル絞り込みだけAPIに列追加が要るので、**初版に含めるか（推奨）／検索＋未設定のみで一旦出すか**を要確認。

## 4. 実装計画（段階）

区切りごとにレビュー・デプロイできる粒度で分ける。

### 区切り1: バックエンド

- 既存 `upsert_item_target` の中身を「1件を処理して行を返す」共通関数に切り出す（算出式の共有）。
- `POST /api/item-targets/bulk` を追加（上記Q1の仕様、1トランザクション）。
- `GET /api/item-targets` のレスポンス各行に `genre_u1/u2/u3` を追加（Q2のジャンル絞り込み用。直近実績→マスタカテゴリの順で解決）。
- テナント（UserScopedMixin）はモデルで自動適用されるため、bulk でも既存と同じく現ユーザー範囲に閉じる（追加対応不要な想定だが実装時に確認）。

### 区切り2: フロント（本命UI）

- 入力を uncontrolled onBlur から「編集中の値を保持する仕組み」に変更（管理番号キーの pending Map など）。編集された行に「未保存」印を付ける。
- 「一括保存」ボタンを追加 → `POST /api/item-targets/bulk` に編集分だけ送る → 完了後に1回だけリロード。
- 絞り込みUI: キーワード検索・「未設定のみ」トグル・ジャンル選択（区切り1で列が入れば）。
- 既存の推定値の承認・再計算ボタンはそのまま残す（一括保存とは別導線）。

### 区切り3（任意・第2段階）: CSV入出力

- `masters.py` の作法を流用して `GET /api/item-targets/export?year_month=` と `POST /api/item-targets/import` を追加。
- CSV列（案）: `管理番号, 商品名, 対象月, 目標売上`（対象月を列に持たせて月混在も許容するか、月固定で持たせないかは実装時に決める）。往復（エクスポート→編集→インポート）を成立させる。
- インポートは bulk と同じ共通関数を使って算出式を共有。

### 検証（各区切り共通）

- ローカルでサンプルデータ再生成 → 一括保存で複数件の `target_sales` がまとめて保存され、必要アクセス等が算出されること。
- 絞り込み（検索・未設定のみ・ジャンル）が正しく効くこと、絞り込み結果外の行を触らないこと。
- 推定値の承認フローが一括保存後も従来どおり動くこと。
- 本番デプロイ後に `/api/security-status` ok:true と実画面確認。

## 5. 留意点・確認したいこと（まとめ）

- **性能の割り切り**: bulk は初版で per-item calc のループ（プリフェッチ最適化はしない）。低頻度操作なので許容、の判断でよいか。
- **ジャンル絞り込みを初版に含めるか**: 一覧APIへの列追加が要る。推奨は初版から入れる。
- **CSVは第2段階に回す**方針でよいか（初版はテーブル一括編集のみ）。
- 既存の1件POST（onBlur即時保存）は残す方針（後方互換・単発編集用）。
