## 1. データ量の試算（4万SKU店舗）

| データ | 行数/年 | 容量/年 |
|---|---|---|
| 月次商品分析（全SKU×12ヶ月） | 48万行 | 0.24 GB |
| RPP週次（出稿25%と仮定×52週×2テーブル） | 104万行 | 0.52 GB |
| **現行設計の合計** | **152万行** | **約 0.8 GB/年** |
| （参考）日次売上を将来追加した場合 | 1,460万行 | **7.3 GB/年** ★ |

- **現行の週次/月次設計なら、4万SKUでも重くない。** Supabase Pro（8GB）で複数店舗×数年持つ
- **「日の売上データ」を生で入れ始めると桁が変わる**（7GB/年/店舗）。日次対応をやる時は
  保持期間（例: 直近90日だけ日次、以前は週次に集約）とパーティション設計を先に決めること。
  今日は入れ物だけ決めて、日次設計は機能実装時の課題とする
- CSV取込のピークメモリ: 商品分析4万行 ≈ 12MB → pandas展開で **100〜150MB**。
  512MBのコンテナだとFastAPI本体と合わせてギリギリ。2GBなら余裕

## 2. 現状構成と問題点

| レイヤー | 現在 | 問題 |
|---|---|---|
| アプリ (FastAPI+React) | Render **Free・Oregon** | ①アイドルで停止→初回50秒待ち ②**DBが東京なのにアプリはオレゴン**。全クエリが太平洋往復（+100ms以上）で、画面表示のたびに積み重なる ③512MB相当でCSV取込が不安 |
| DB・認証 | Supabase **Free・東京** | ①1週間アイドルでDB一時停止 ②**自動バックアップなし**（顧客データを預かるのに） ③500MB制限 → 4万SKU店舗1つで1年持たない |
| LP | Vercel **Hobby** | **Hobbyプランは商用利用が規約違反**。商用LPを置くならPro($20/月)が必要 |
| ドメイン | なし（*.onrender.com / *.vercel.app） | URLに信頼感がない。審査・営業の観点でも独自ドメイン推奨 |
| メール | Gmail SMTP（未設定） | 当面は可。日500通制限 |

**リージョン問題は公開前の今が直すラストチャンス。** RenderはリージョンA変更不可のため
シンガポールに新サービスを作り直す形になり、URLが変わる。公開後だとStripe Webhook・
ユーザーへの案内すべてに影響するが、今なら影響ゼロ。さらに独自ドメインを挟めば
今後どこへ移してもURLは不変になる。

### 節約版（合計 $32/月）との比較

Render Starter($7)でも動くが、4万SKUのCSV取込でメモリ死する懸念があり、
落ちたときの調査時間の方が高くつく。差額$18は保険として妥当と判断。

### 大きな構成変更（Fly.io東京・Cloud Run等への全面移行）を勧めない理由

レイテンシだけならRenderシンガポールで十分改善し、デプロイ手順・ドキュメント・
CLAUDE.mdの前提を書き換えずに済む。終盤での大移行はリスクが利益を上回る。

## 4. 移行手順（決定後の作業順）

1. ドメイン取得（Cloudflare）
2. Supabase Pro にアップグレード（ダッシュボードでボタン1つ・ダウンタイムなし）
3. Render に Singapore リージョンで新サービス作成 → 環境変数を移す →
   `app.ureshiru.com` をカスタムドメインに設定
4. Stripe の Webhook URL・ビジネスサイトURL、Supabase の Redirect URL を新ドメインに更新
5. LP を Cloudflare Pages に載せ `ureshiru.com` を割当（Root Directory=lp、GitHub連携）
6. `lib/links.ts` の `LP_BASE_URL`、LPの canonical/OGP を独自ドメインに更新
7. 旧 Render サービス・Vercel プロジェクトを削除（DNS切替の確認後）

所要: 半日程度。Stripe審査待ちの間に完了できる。
