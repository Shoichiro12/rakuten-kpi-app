## パート1: 知識（次にUIを触るときの参照）

### 1-1. ウレシルで採用する原則

| 原則 | 中身 | 根拠 |
|---|---|---|
| **強調は1画面に1つ** | 最も重要な数値（KGI達成状況）だけ大きく、他は沈める。カードを全部同じ強さで並べない | 実務系SaaS共通。区切りCのダッシュボード3層構成はこれを既にやっている |
| **アクセント色は1〜2色まで** | 基本はグレー階調。色は「意味があるとき」だけ使う | muz.liの50例に共通する唯一の実用的な結論。ダーク系もライト系も、色数を絞った例だけが読める |
| **状態色は予約語** | 良い/注意/危険/重大の4つ。この4色を「系列3」「装飾」に流用しない | dataviz。混ざると「赤=悪い」の学習が壊れる |
| **色だけで意味を伝えない** | 状態色にはアイコンかラベルを添える | 色覚特性・白黒印刷・スクショ共有で死なないため |
| **カード単位のモジュール** | 同じ高さ・同じ内側余白のカードを並べる。走査線が予測できる形にする | SaaSFrame側の全例。既にこの形にはなっている |
| **チャートは装飾を削る** | 罫線は極細の実線・軸は控えめ・全点にラベルを置かない | dataviz。実務系SaaSのチャートはどれも線が細い |
| **二軸チャートは作らない** | スケールの違う2指標は2枚に分ける | dataviz「最も多いチャートの間違い」。**ウレシルは現状ゼロ。この状態を守る** |
| **空・読込中・エラーを設計する** | 「データがありません」で画面を消さない。今わかることは出す | VISION.md と一致。実務系SaaSは空状態を専用デザインで持っている（SaaSFrameのMeiroの例） |
| **数値の桁を揃える** | 表の数値列と軸ラベルは `tabular-nums` | dataviz。ただし**大きなヒーロー数値には付けない**（等幅だと間延びする） |

### 1-2. ウレシルでは採用しないもの（と、その理由）

muz.liの50例の大半はポートフォリオ映えのビジュアルで、実データを入れると崩れる。
判断が揺れないよう、採らないものを先に固定しておく。

| 採らないもの | 理由 |
|---|---|
| **ダークテーマ** | 顧客（EC事業者）は日中の事務所で使い、画面をスクショして社内共有・コンサル提出する。白地のほうが刷っても読める。ダーク対応は工数が倍になるわりに利用実態と噛み合わない |
| **ネオンアクセント・グラデーション背景** | 数値の信頼性を下げる。財務・広告費の画面で光らせる理由がない |
| **グラスモーフィズム（すりガラス）** | 背景が透けるぶんコントラストが不安定になり、日本語の細い文字が最初に潰れる |
| **3Dオブジェクト・写真背景** | ウレシルの指標に対応する「モノ」が無い（医療の人体・不動産の間取りのような接地対象が無い） |
| **極端な余白（1画面1指標）** | ウレシルは毎日開いて意思決定する道具。ダッシュボードは情報密度が要る。余白は「読みやすさの範囲で」取る |

### 1-3. 日本語UI固有の注意（参照元は全部英語UIなので、そのまま真似ると崩れる）

- **`uppercase` は日本語に効かない。** ラベルに付けても見た目は変わらず、英数字混じりのときだけ大文字化して不揃いになる
- **`tracking-wide`（字間を広げる）は日本語だと間延びする。** 英語の小さいラベルを締めて見せる技法で、仮名漢字には逆効果
- **10px・11pxの文字を常用しない。** 日本語は同じpxでも情報量が多く、英語より1〜2px大きく必要。参照元の「小さいラベル」をそのままpx置き換えすると読めなくなる
- **ラベルが長い。** 「想定追加広告費」「アイテム別目標」など、英語UIの2倍の幅を食う。カードの横並び数は英語のデザイン例より1つ減らす前提で組む

## パート2: ウレシルの現状診断

`frontend/src/` の全42ファイル・9,743行を実測した結果。印象ではなく出現回数で出している。

### 2-1. 実測値

| 項目 | 実測 | 評価 |
|---|---|---|
| 文字サイズの種類 | **10種類**（text-xs 317 / text-sm 216 / `text-[10px]` 94 / `text-[11px]` 53 / text-xl 11 / text-lg 8 / text-2xl 8 / `text-[9px]` 6 / text-base 4 / text-3xl 3） | 多すぎ。うち3種類はTailwind外の直値 |
| 12px未満の文字 | **153箇所**（10px/11px/9px） | 日本語では小さすぎる。9pxは実質読めない |
| 角丸の種類 | **6種類**（rounded-lg 134 / rounded 117 / rounded-xl 93 / rounded-full 21 / rounded-2xl 8 / rounded-md 4） | 3種類（sm/lg/full相当）に整理できる |
| 色ファミリ | **11種類**（gray 895 / blue 181 / red 146 / green 141 / amber 134 / violet 51 / emerald 15 / sky 12 / orange 10 / purple 5 / indigo 1） | 多い。green と emerald、blue と sky と indigo が混在 |

| 影の種類 | **6種類**（shadow-sm 59 / md 3 / xl 2 / lg 2 / 2xl 1 / shadow 1） | shadow-sm 以外はほぼ事故。1〜2種類でよい |
| カード定義の文字列 | **12パターン**（`bg-white rounded-xl border shadow-sm p-4` ほか） | 同じ意味のカードが12通りの書き方で存在 |
| チャート内の色の直値 | **25種類以上のhex** | トークン化されていない |
| 二軸チャート | **0** | 良い。この状態を守る |
| 空状態のガード | 主要画面にあり | 良い。VISIONと整合 |

### 2-2. 優先度つきの課題

#### 優先度: 高

**A. 色の意味づけが決まっていない（色ファミリ11種類）**

`green` と `emerald`、`blue` と `sky` と `indigo` が同じ画面に混在している。
`violet` は「手動補正」バッジ、`amber` は「未確認の提案」と警告の両方で使われていて、
色を見ただけでは状態なのか分類なのか判別できない。

やること: 状態4色（良い/注意/危険/重大）と、それ以外に使う中立色を決めて表にする。
`emerald`・`sky`・`indigo`・`purple`・`orange` は原則廃止して既存4色に寄せる。

**B. 12px未満の文字が153箇所**

`text-[9px]`（6箇所）は日本語では実質読めない。`text-[10px]` 94箇所も注記の常用サイズになっている。
Web Interface Guidelines のアクセシビリティ観点でも、日本語の可読性の観点でも下限を上げたい。

やること: 最小を12px（`text-xs`）に統一し、9px/10px/11px は 11px（1種類だけ残す）か 12px に寄せる。

**C. 日本語ラベルに `uppercase tracking-wide` が付いている**

`KPICard.tsx` のラベル（`font-medium uppercase tracking-wide`）と `Sidebar.tsx` の「楽天EC」。
`uppercase` は日本語に効かず、`tracking-wide` は字間が空いて締まりが無くなる。英語UIの真似が
そのまま残っている箇所。

やること: 日本語ラベルからは両方外す。

#### 優先度: 中

**D. チャートの罫線が破線**

`KPIChart.tsx` の3箇所すべてが `CartesianGrid strokeDasharray="3 3"`。
破線は「しきい値」「予測」の意味に読まれるので、ただのグリッドに使うとノイズになる。

やること: 実線の極細（1本、地の色から1段だけ濃い程度）に変える。

**E. 単系列のチャートに凡例が出ている**

`KPIChart.tsx` の単系列 `LineChart` に `<Legend />` がある。系列が1本ならタイトルが名前を兼ねるので、
凡例の箱は場所の無駄。複数系列（`MultiLineChart`）には必要。

やること: 単系列では凡例を出さない。

**F. チャートの色が呼び出し側から個別に渡っている**

`color` プロップと `metrics[].color` で、呼び出しごとに hex を直書きしている（既定は `#2563eb`）。
このままだと同じ指標が画面ごとに違う色になったり、系列を絞り込んだときに色が入れ替わったりする。

やること: 指標名から色を引く対応表を1箇所に置き、呼び出し側は色を渡さない。

**G. カードの書き方が12パターン**

やること: `Card` コンポーネント（もしくはクラス定数）を1つ作り、`p-4`（標準）・`p-5`（強調）・
`overflow-hidden`（表を入れるとき）のバリアントで吸収する。

#### 優先度: 低（やる価値はあるが急がない）

**H. 影が6種類** … `shadow-sm` 以外は1〜3箇所の孤立使用。統一する。

**I. 角丸が6種類** … `rounded-lg`（部品）・`rounded-xl`（カード）・`rounded-full`（バッジ）の3つに寄せる。

**J. 表の数値列に `tabular-nums` が入っていない** … 現状は年間目標プランナー表の1箇所だけ。
商品別KPI・RPP・GAP・商品マスタの数値列にも入れると桁が揃う。ヒーロー数値には付けない。

**K. ブランド色がほぼ使われていない（16箇所）** … 現状ほぼ無彩色＋汎用blueのアプリ。
「楽天っぽさ」を出すのか、自社サービス（ウレシル）としての色を持つのかは**デザインの意思決定**なので、
勝手に決めずオーナーの判断を仰ぐ。

### 2-3. 診断していないこと

- **実画面の見た目は見ていない。** 本番はログインが必要でこちらからは開けないため、
  診断はすべてコードの実測にもとづく。「実際に並べたときにどう見えるか」は別途確認が要る
- **Dribbble の中身は取得できていない。** 参照できたのは muz.li と SaaSFrame の2つ
- **レスポンシブ（タブレット幅）での検証はしていない**

## 次にやるなら（提案）

1つの区切りにまとめず、影響範囲の小さい順に。

| 区切り | 内容 | 影響 |
|---|---|---|
| 1 | 色・文字サイズ・角丸・影のトークンを決めて CLAUDE.md に表で書く（コードはまだ触らない） | ゼロ。決めるだけ |
| 2 | 課題C（日本語への `uppercase tracking-wide`）とD・E（チャートの破線・単系列の凡例）を直す | 小。見た目が締まる |
| 3 | 課題B（12px未満）を一括置換 | 中。全画面の文字が少し大きくなる |
| 4 | 課題A（色の統一）と G（カード共通化） | 大。まとめて触る必要がある |

課題K（ブランド色）はオーナーの意思決定待ちなので、この順番には入れていない。
